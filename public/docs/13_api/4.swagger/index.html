Creando un swagger

Qué es swagger y para qué sirve

Formas de realizar la descripción

De alguna forma debemos de describir el funcionamiento de nuestra api

Principalmente para cada entrypoint: Cómo es la url Qué datos retorna Qué errores puede producir ….

Instalando la librería

1 composer require darkaonline/l5-swagger
  1. Publicamos la configuración 
    1 php artisan vendor:publish --provider="L5Swagger\L5SwaggerServiceProvider"
  2. Establecemos variables de configuración en el fichero .env 
     1## Describiendo su comportamiento
 2Podemos hacerlo con comentarios o bien con un fichero descriptivo de tipo yaml
 3
 4Vamos a tomar esta segunda opción
 5
 6
 7### Especificando el comportamiento de swagger en nuestro diseño 
 8# --- L5-Swagger (documentación API) ---
 9L5_SWAGGER_GENERATE_ALWAYS=true
10L5_SWAGGER_CONST_HOST="${APP_URL}"
11L5_SWAGGER_BASE_PATH=/api
12L5_FORMAT_TO_USE_FOR_DOCS=yaml
13L5_SWAGGER_OPEN_API_SPEC_VERSION=3.0.0
Variable Valor en desarrollo Descripción
L5_SWAGGER_GENERATE_ALWAYS true Regenera automáticamente la documentación OpenAPI en cada petición. Resulta cómodo durante el desarrollo, pero en producción se recomienda establecerlo a false para mejorar el rendimiento.
L5_SWAGGER_CONST_HOST ${APP_URL} Define la URL base de la aplicación que se utilizará en las anotaciones y en la documentación generada.
L5_SWAGGER_BASE_PATH /api Indica el prefijo común de las rutas de la API, normalmente coincidente con las rutas definidas en routes/api.php.
L5_FORMAT_TO_USE_FOR_DOCS json Especifica el formato de la documentación generada. Swagger UI cargará el fichero api-docs.json.
L5_SWAGGER_OPEN_API_SPEC_VERSION 3.0.0 Versión de la especificación OpenAPI utilizada para generar la documentación. OpenAPI 3.0 es la versión más habitual en proyectos docentes y profesionales.

  1. Personalizar config/l5-swagger.php 

     1   'title' => 'API Alumnos DGA',
 2
 3    'api' => 'api/documentation',
 4    
 5      'annotations' => [
 6          base_path('app'),
 7       ],
 8
 9    'docs' => storage_path('api-docs'),
10
11    'generate_always' => env('L5_SWAGGER_GENERATE_ALWAYS', false),
12
13    'constants' => [
14         'L5_SWAGGER_CONST_HOST' => env('L5_SWAGGER_CONST_HOST', 'http://my-default-host.com'),
15    ],

  2. Creamos el link para el storage

1php artisan storage:link
  1. Se puede acceder a la url http://localhost:8000/api/documentation

Creando anotaciones

El fichero yaml contendrá algún dato obligatorio:

Vamos de forma creciente creando el fichero entendiendo la información que vamos aportando.

Información básica

Estos elementos son obligatorios

Elemento Ubicación Función
info Raíz del documento Define la información general de la API: título, versión, descripción, términos de uso, contacto y licencia.
servers Raíz del documento Lista los servidores donde está disponible la API. Swagger UI utilizará el primero por defecto.
paths Raíz del documento Contiene todos los endpoints de la API agrupados por URL. 

1openapi: 3.0.0
2
3info:
4title: API Gestión de Alumnos
5version: 1.0.0
6
7paths:{}
Con esto ya podríamos tener una primera versión mínima (no operativa), de nuestro swagger

Aportando los entrypoints

A continuación aportarmeos información para cada uno de los o entrypoint, igualmente vamos de forma general al detalle. Para ello crearemos un elemento por verbo http que corresponde a un rest full

PAra cada verbo vamos a agregar un argumento que es el summary o título

 1paths:
 2/students:
 3    get:
 4        summary: Listar alumnos
 5    post:
 6        summary: Insertar un alumno
 7    delete:
 8        summary: Eliminst un alumno
 9    put:
10        summary: Modificar todos los datos de un alumno
11    patch:
12        summary: Modificar algún dato de un alumno

Además del summary podemos (debemos aportar el código de respuesta con una descripcción)

 1openapi: 3.0.0
 2
 3info:
 4title: API Gestión de Alumnos
 5version: 1.0.0
 6
 7paths:
 8    /students:
 9        get:
10            summary: Listar alumnos
11            responses:
12                '200':
13                    description: Operación correcta
14        post:
15            summary: Insertar un alumno
16            responses:
17                '201':
18                    description: Se ha incorporado el nuevo studiante
19        delete:
20            summary: Eliminado un alumno
21            responses:
22                '204':
23                    description:Alumno eliminado
24        put:
25            summary: Modificar todos los datos de un alumno
26            responses:
27                '200':
28                    description: Se han modificado todos los datos de un alumno 
29        patch:
30            summary: Modificar algún dato de un alumno
31            responses:
32                '200':
33                    description: Se han modificado todos los datos de un alumno
Elemento Función
/students Recurso de la API.
get Verbo HTTP utilizado para consultar recursos.
summary Descripción breve de la operación.
responses Lista de respuestas posibles.
200 Código HTTP que indica éxito.
description Explicación de la respuesta.

Añadiendo parámetros

Ahora la descripción empieza a hacer que el fichero crezca Es el momento de describir de forma detallada cada item del recurso

Elemento Función
parameters Lista de parámetros de entrada.
name Nombre del parámetro.
in Ubicación del parámetro (path, query, header o cookie).
required Indica si el parámetro es obligatorio.
schema Define el tipo de dato.
type Tipo del dato (string, integer, boolean, etc.).

En nuestro caso (lo hacemos para get) 

 1paths:
 2/students/{id}:
 3    get:
 4        summary: Obtener alumno
 5        parameters:
 6            - name: id
 7              in: path
 8              required: true
 9              schema:
10                type: integer
11            - name: name
12              in: path
13              required: true
14              schema:
15                type: string
16            - name: email
17              in: path
18              required: true
19              schema:
20                type: string
21            - name: age
22              in: path
23              required: true
24              schema:
25                type: integer
26
27      responses:
28        '200':
29          description: Alumno encontrado

Describiendo el contenido de la respuesta

Ahora toca especificar cómo es cada respuesta, según estos paráemtros

Elemento Función
content Describe el contenido devuelto por la API.
application/json Tipo MIME de la respuesta.
schema Estructura de los datos devueltos.
properties Lista de atributos del objeto.
example Ejemplo de respuesta.

En nuestro ejemplo: 

 1paths:
 2/students/{id}:
 3    get:
 4      summary: Obtener alumno
 5      parameters:
 6        - name: id
 7          in: path
 8          required: true
 9          schema:
10            type: integer
11      responses:
12        '200':
13          description: Alumno encontrado
14          content:
15            application/json:
16              schema:
17                type: object
18                properties:
19                  id:
20                    type: integer
21                  name:
22                    type: string
23                  email:
24                    type: string
25                  age:
26                    type: integer
27              example:
28                id: 1
29                name: María Rodríguez
30                email: juan@example.com
31                age: 18

Fase 6. Definición de modelos

En lugar de repetir la definición de un alumno en cada endpoint, podemos crear un modelo reutilizable.

 1components:
 2
 3schemas:
 4
 5    Student:
 6
 7      type: object
 8
 9      required:
10        - id
11        - name
12        - email
13
14      properties:
15
16        id:
17          type: integer
18
19        name:
20          type: string
21
22        email:
23          type: string
24
25        age:
26          type: integer

Ahora podemos reutilizarlo en cualquier respuesta:

 1responses:
 2
 3'200':
 4description: Alumno encontrado
 5
 6    content:
 7      application/json:
 8
 9        schema:
10          $ref: '#/components/schemas/Student'

Fase 7. Definición de errores

 6'404':

 9'500':

 7      type: object
 8
 9      properties:
10
11        status:
12          type: integer
13

15          type: string

17        detail:
18          type: string

Fase 8. Cabeceras HTTP

Además de los parámetros de ruta o consulta, las peticiones HTTP pueden incluir información adicional en las cabeceras.

 1parameters:
 2
 3- name: Accept
 4  in: header
 5  required: true
 6
 7  schema:
 8  type: string
 9
10- name: Content-Type
11  in: header
12  required: true
13
14  schema:
15  type: string
16

Fase 9. Cabeceras obligatorias en JSON:API

El estándar JSON:API exige el uso del tipo MIME application/vnd.api+json.

 1parameters:
 2
 3- name: Accept
 4  in: header
 5  required: true
 6
 7  schema:
 8  type: string
 9  default: application/vnd.api+json
10
11- name: Content-Type
12  in: header
13  required: true
14
15  schema:
16  type: string
17  default: application/vnd.api+json
18

Una petición real tendría este aspecto:

1GET /api/students/1 HTTP/1.1
2Accept: application/vnd.api+json
3Content-Type: application/vnd.api+json

Fase 10. Componentes reutilizables para JSON:API

Como estas cabeceras se utilizarán en muchos endpoints, resulta conveniente reutilizarlas.

 1components:
 2
 3parameters:
 4
 5    AcceptJsonApi:
 6
 7      name: Accept
 8      in: header
 9      required: true
10
11      schema:
12        type: string
13        default: application/vnd.api+json
14
15    ContentTypeJsonApi:
16
17      name: Content-Type
18      in: header
19      required: true
20
21      schema:
22        type: string
23        default: application/vnd.api+json

Posteriormente podremos utilizarlas mediante referencias:

1parameters:
2
3- $ref: '#/components/parameters/AcceptJsonApi'
4
5- $ref: '#/components/parameters/ContentTypeJsonApi'
6

Fase 11. Autenticación

Muchas APIs requieren que el cliente se autentique mediante un token.

Primero definimos el mecanismo de autenticación:

1components:
2
3securitySchemes:
4
5    BearerAuth:
6
7      type: http
8      scheme: bearer
9      bearerFormat: JWT

Y después indicamos qué operaciones lo requieren:

1security:
2
3- BearerAuth: []
4

La petición incluiría una cabecera similar a:

1Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
